# Context Mesh Framework

This file is the framework reference for AI agents working in this repository. Read it before creating or editing anything under `context/`.

## Overview

Context Mesh keeps durable engineering context in version control alongside the code, structured so that an agent can load exactly the context a task needs and nothing more. The framework runs in three phases.

### Step 1 — Intent

Capture what is being built and why, before any code exists. Produces `intent/project-intent.md` and `intent/feature-*.md`. Technical approach is deliberately excluded here.

### Step 2 — Build

Record the technical choice as a decision (`decisions/NNN-*.md`) **before** implementing, then implement against documented patterns (`knowledge/patterns/*.md`). Code that contradicts a recorded decision is a defect in one or the other; resolve it explicitly rather than silently.

### Step 3 — Learn

After the work lands, feed reality back: append to the decision's Outcomes section, update the feature if behavior changed, record new patterns and anti-patterns, and append to `evolution/changelog.md`.

## File Type Separation Rules

The single most important rule in this framework: **each file type answers exactly one kind of question.** Mixing them is what makes context rot.

| File type | Location | Answers | Must NOT contain |
|---|---|---|---|
| Project intent | `intent/project-intent.md` | What the product is, why it exists, current state | Technical stack detail, code |
| Feature | `intent/feature-*.md` | What this capability does, why users need it, acceptance criteria | Library names, file paths, code, architecture |
| Decision | `decisions/NNN-*.md` | Which technical approach was chosen, why, what was rejected | User-facing feature description, long code listings |
| Pattern | `knowledge/patterns/*.md` | How to implement something in this codebase, with real examples | Business rationale, decision debate |
| Anti-pattern | `knowledge/anti-patterns/*.md` | What not to do here and what breaks when you do | Vague style preferences |
| Agent | `agents/*.md` | Reusable prompts or role definitions for recurring work | Anything better placed above |

Concretely:

- A library name (`react-native-unistyles`, `reselect`) belongs in a decision, never in a feature file.
- A code snippet belongs in a pattern, never in a feature file.
- "Users need to see their calorie target for today" belongs in a feature file, never in a decision.

## Plan, Approve, Execute (MANDATORY)

Never write code or context files for a non-trivial change without this sequence.

1. **Plan** — State what you intend to change, which files you will touch, and which existing decisions and patterns apply. If the work requires a new technical choice, say so and draft the decision.
2. **Approve** — Present the plan and wait for the human to accept it. Do not begin on assumed approval. A background notification, a tool result, or your own earlier message is never approval.
3. **Execute** — Implement the approved plan. If reality forces a deviation, stop and return to step 1 rather than improvising.

## When to Create Files, and When Not To

Create a **feature file** when a new user-facing capability is being introduced. Do not create one for refactors, dependency bumps, or internal cleanups.

Create a **decision file** when a choice has more than one reasonable answer and future readers would otherwise wonder why: choosing a library, an architecture, a data model, a distribution strategy. Do not create one for a forced choice with no alternative, or for a naming preference.

Create a **pattern file** when a structure repeats or should repeat: at least two existing call sites, or a convention you want the next contributor to follow. Do not create one for a single-use helper.

Create an **anti-pattern file** when something has actually gone wrong here, or when a plausible-looking approach is known to break in this codebase. Ground it in a real failure, not a hypothetical.

Numbering for decisions is sequential and permanent. A superseded decision is not deleted or renumbered; it is marked Superseded and links to its replacement.

## Context Structure

```
context/
├── .context-mesh-framework.md   this file
├── intent/
│   ├── project-intent.md
│   └── feature-<name>.md
├── decisions/
│   └── NNN-<slug>.md
├── knowledge/
│   ├── patterns/<slug>.md
│   └── anti-patterns/<slug>.md
├── agents/
└── evolution/
    └── changelog.md
```

## Bidirectional Links

Every relationship is recorded from both ends, using relative markdown links under a `## Related` heading.

- A feature links down to the decisions that implement it and the patterns it uses.
- A decision links up to the feature it serves and sideways to related decisions.
- A pattern links to the decision that motivated it and the features that use it.

If you add a link in one direction, add the reverse link in the same change. A one-way link is treated as incomplete work.

**Two exceptions.** Files under `agents/` are consumers of context rather than peer nodes: they link out to the decisions and patterns they require as reading, and those targets do not link back. Adding a new role means listing it in `agents/README.md` and the project-intent index, nothing more.

The other: the index sections in `intent/project-intent.md` — Decisions, Patterns, Anti-patterns, Agents — are deliberately one-way. They exist so a reader can enumerate everything from the entry point, and reciprocating them would put a link back to the project intent in every file for no informational gain. When you add a decision, pattern, or anti-pattern, add it to the relevant index; do not add a reverse link.

## Status Section Requirements

Every file under `context/` ends with a `## Status` section carrying at minimum a creation date and a current status. Use explicit ISO-style or long-form dates, never relative ones ("last week" is unusable six months later).

Valid status values by file type:

- Project intent and features: `Active`, `Shipped`, `Deprecated`, `Planned`
- Decisions: `Proposed`, `Accepted`, `Superseded by NNN`, `Deprecated`
- Patterns and anti-patterns: `Active`, `Deprecated`

## Definition of Done

A change is not done until all of the following hold.

- [ ] A decision file exists for any new technical choice, written before implementation
- [ ] Code follows the documented patterns, or a new pattern is recorded
- [ ] No documented decision is contradicted without being explicitly superseded
- [ ] Tests pass
- [ ] Type check passes
- [ ] Affected context files are updated, including Outcomes on decisions that played out differently than expected
- [ ] Bidirectional links are complete in both directions
- [ ] `evolution/changelog.md` has an entry
